# 各話のレビュー・修正ループ

## 目的と役割

一般の読者が、作者の補足説明なしに出来事・因果・人物の気持ちを追える本文にする。

- 親エージェント：本文執筆、修正、資料更新、レビュー記録を担当する。
- レビュアー：必ず `gpt-6-luna` のサブエージェントを使う。本文や設定資料を編集させない。
- Luna が理解できなかった箇所は、作者だけが補っている論理のギャップとして扱う。「モデルの理解力の問題」「設定を読めば分かる」で退けない。必要な手掛かりを本文に書き、再レビューで解消を確認する。
- 指摘を消すためにレビュー基準を緩めたり、指摘を隠したり、作者の説明に納得させたりしない。

## 対象と資料

パスはリポジトリルートからの相対パス。

- 本文の正本：`manuscript/NN.txt`。空なら未執筆と報告し、合格にしない。執筆依頼もある場合は初稿を書いてから実行する。
- 設定：`planning/concept.md`、`planning/characters.md`、`planning/world.md`。
- 構成・未決事項：`planning/outline.md`、`planning/open-questions.md`、存在する場合の `planning/episode-NN.md`。
- 継続性・進捗：`planning/continuity.md`、`planning/progress.md`。
- 投稿書式：`publishing/format.md`、`publishing/checklist.md`。

各話を順番に扱う。前の話を変更した場合は、影響する後続の既稿もレビュー対象に戻す。`publishing/` に本文のコピーを作らない。文頭の話数・タイトルと文字数の数え方は `publishing/format.md` に従い、タイトル行を含むファイル全体をレビュー・ハッシュ確認の対象とする。作者用レビュー記録は本文に挿入しない。

## 1. レビューの準備

親は対象本文、関連資料、既稿を読み、今回の対象範囲を把握する。レビュー対象の本文は周回中に変更せず、開始時に SHA-256 を記録する。ハッシュは改行コード・BOMを含む実ファイルのバイト列から算出する。PowerShell では `Get-FileHash -Algorithm SHA256 -LiteralPath <対象本文の絶対パス>` を使い、親も Luna も同じファイルを計算する。文字列として読み直した内容からは計算しない。

読者に提示済みの前話までの本文を文脈として使う。作者用あらすじで代用しない。長い場合は Luna が本文を分割して読む。必要な既稿が読めなければ、読んだ範囲と未確認範囲を明示し、全体確認済みとはしない。

## 2. Luna に二段階でレビューを依頼する

各周回で新しいサブエージェントを作成する。`collaboration.spawn_agent` に `model: "gpt-6-luna"`、`fork_turns: "none"`、一意な `task_name` を指定する。作者の会話・過去のレビュー・修正意図を引き継がせない。モデル変更のために全履歴を継承する指定は使わない。

モデルを指定できない、起動に失敗する、または別モデルになる場合は、Luna レビューを完了扱いにしない。既に受け取った未対応の指摘があれば修正できるが、レビュー結果がなければこのループでは本文を変更せず、未完了の理由と再開条件を記録する。別モデルや親の自己レビューで代用して合格を出さない。

### 第一段階：本文だけで読めるか

次の依頼文に絶対パスと対象話を埋めて送る。この段階では、このスキル全文や作者用資料を渡さない。

```text
あなたは一般読者の視点で小説をレビューする担当です。ファイルは編集しないでください。
レビュー・修正ループの管理は親が行います。あなたは別のエージェントを起動せず、レビュー結果だけを返してください。
対象本文：{対象話の絶対パス}
読者に提示済みの文脈：{前話までの本文の絶対パス一覧。第1話では「なし」}
対象本文と、上に列挙された前話までの本文を読んでください。作者用資料や列挙されていないファイルは参照しないでください。

読者が知り得る情報だけで、誰が、どこで、何をし、なぜその結果になったかを追ってください。
主語、位置や時間の移動、行動の動機、感情の変化、能力の条件・代償、会話の応答に、
理解できない点や複数の解釈に分かれて筋を追えない点があれば具体的に挙げてください。
通信技術やファンタジーの専門知識を前提にしすぎる語句や比喩、説明不足・冗長な説明も確認してください。
推測で作者の論理を補わず、どの語句・前提・つながりが不足しているかを書いてください。
意図的な謎は、現時点の行動や出来事を理解できるなら説明不足と区別してください。
単なる好みの言い換えを必須の指摘にしないでください。

出力：
1. 読んだファイルと範囲、対象本文の SHA-256（Get-FileHash -Algorithm SHA256 -LiteralPath で実ファイルのバイト列から計算）
2. 理解した出来事と因果の短い要約（推測は明示）
3. 各指摘の ID、重要度（Critical / Important / Minor）、箇所（ファイル・行と短い引用）、
   読者が理解できない点または具体的な問題、本文で補うべき情報・修正意図
4. 未確認範囲・未解消の疑問、重要度別の指摘件数
問題がなければ「第一段階の指摘ゼロ」と明記してください。
```

親は返答を受け取り、読み取り範囲と要約を確認する。要約が本文の意図と食い違う場合は理解のギャップとして記録する。成功判定を得るための解説は送らない。

### 第二段階：設定・構成との整合

同じ Luna に `collaboration.followup_task` で「対象と資料」に列挙した設定・構成・未決事項・継続性・進捗・投稿書式の各ファイルを絶対パスの一覧として渡す。`planning/episode-NN.md` だけは存在するときに追加する。存在しない必須資料は不足として記録する。依頼はレビューのみとし、編集や追加エージェントの起動をさせない。次を確認させる。

- 第一段階の指摘を保持したまま、設定・構成・時系列・書式との整合を追加確認する。
- 作者用資料を読んで意味が分かっても、本文側の理解不足の指摘は取り下げない。
- 提示設定と仮案・未決事項を区別し、仮案との差だけを矛盾と断定しない。
- `publishing/format.md` の編集方針案も同様に扱う。未採用の案との差だけでは必須指摘にせず、実際の読みにくさ、本文内の表記不統一、投稿時の表示不具合、または採用済みの方針との不一致を根拠にする。
- トーヤ、リーシャ、ガルド、ミミルらの知識・技能・口調と、場面ごとの視点を確認する。一人称など未決の項目を勝手に確定設定として扱わない。
- 車両・端末・中継局の所在、地形と通信範囲、電源・燃料・魔石の消耗、端末の残数、接続数と通話容量、再召喚の間隔、能力の発展段階を確認する。地球のインターネットやGPS衛星に依存する解決、未解禁の設備、通信圏外との根拠のない接続、単独基地局による根拠のない精密測位を混入させない。通信成立と情報の真偽を区別し、暗号化だけで電波妨害が解消する描写にしない。
- 「世界中の人が話せるようになれば、世界は平和になるのか」という問いに対し、通信の恩恵と弊害、人々自身の選択、主人公と現地の人々の関係が具体的な出来事として描かれているか確認する。序盤から全テーマの説明を要求せず、対象話の役割に即して評価する。
- 第一段階と同じ形式で、両段階を合わせた全指摘、重要度別件数、未確認範囲を報告する。全件解消なら「両段階の指摘ゼロ」と明記する。

## 3. 親が本文を修正する

両段階の全指摘を整理し、Critical → Important → Minor の順に修正する。理解不足は必ず本文で扱う。修正案をそのまま採用する必要はないが、指摘された読者のつまずきは解消する。

- 主体・行動・結果をつなぐ文、必要な位置や時間の手掛かり、感情が変わるきっかけを該当場面に補う。
- 抽象的な結論だけで進めず、見える動作・会話・感覚で意味を伝える。固有語は文脈から働きが分かるようにする。
- 設定を一括説明するだけにせず、理解に必要な情報を必要な場面に置く。人物の声、伏線、笑いを保つ。
- 意図的な謎の答えは伏せてよいが、人物が今何に困り、何を選んだかは追えるようにする。
- 設定上成立しない修正案には、確定設定を保つ別の本文修正を行う。設定変更が必要なら資料を更新し、未決事項を黙って確定済みにしない。

重複指摘は対応をまとめてよい。引用違いなどの客観的な誤指摘は根拠を記録する。ただし親の判断だけでゼロ件にせず、次の独立レビューで再確認する。

修正後は新しい Luna で手順1〜3を繰り返す。前回の指摘箇所だけでなく、毎回対象話の全文を両段階で確認させ、新しく生じた問題も修正する。

## 4. 記録と終了条件

レビューを実施した時点、または起動不能などで未完了となった時点で `planning/reviews/NN.md` を作成または追記する。未実施の場合はその旨、理由、再開条件を記録し、周回数や結果を捏造しない。 起動前に失敗してエージェントIDがない場合は「該当なし（起動前）」とする。モデルは要求した名前を記録し、実際の起動を確認できなければ「未起動／未確認」と明記する。周回番号、日時、Luna のエージェントID・指定モデル、読んだ範囲、対象本文の SHA-256、全指摘と根拠、対応内容、再レビュー結果を残す。作者用記録を本文へ混ぜない。

以下をすべて満たしたときだけ、その話のレビュー完了とする。

1. 最新本文の全文に対し、Luna の二段階レビューが完了している。
2. Critical / Important / Minor のすべてがゼロで、未解消の理解不足・未確認範囲もない。
3. 親が確認した要約にも意図との食い違いがない。
4. 最終レビューの SHA-256 と現在の本文が一致し、その後に本文を変更していない。
5. 関連する設定・継続性・進捗の記録が本文と整合している。

最終レビュー後に本文を変更した場合は、再びレビューする。レビュー合格だけで公開済みや投稿準備完了にはせず、`planning/progress.md` のメモへ記録のリンクを追加する。投稿準備完了には別途投稿チェックを終える。

周回数を理由に指摘を残して完了しない。同じ理解不足が続く場合は、文単位の追記から場面の順序・情報提示の見直しへ修正方法を変える。ユーザーによる中断、実行環境の制約、またはユーザーしか決められない設定判断で継続できない場合は「未完了」として残件と再開条件を記録する。

各話の完了時は、話数、周回数、主な修正、最終件数、記録の場所を簡潔に報告する。コミット・push・カクヨム投稿は、このスキルの起動だけでは行わず、その時点のユーザーの依頼範囲に従う。
